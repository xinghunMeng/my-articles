# 生产环境可逆数据清理工具的设计与实现（Fastify/Prisma/SQLite 场景）

category: 后端工程

## 背景

宝可问答助手小程序原本跑在微信云开发上（9 个云函数 + 9 个 Records 集合）。近期因接入 QQ 端、且云开发调用量逼近 20 万次/月的套餐上限，我把后端迁到了自建服务 pokemon-back：Fastify 5 + Prisma 6 + SQLite，TypeScript，部署在腾讯云 Ubuntu 上（PORT=3200，PM2 常驻，Nginx 反代 + HTTPS）。

迁移不是把云函数改成接口那么简单。联调时经常要"重置某用户某天的进度"——也就是删除 `Record` 表里 `(userId, date)` 这一个切片。裸 SQL 在生产库上太危险：一旦删错整张表或误伤其它用户，几乎没有回头路。于是我把这套"清理"固化成一个带四道防线的小工具 `scripts/clear-day.ts`。

## 工具设计：四道防线

1. 删前快照：删除前先把命中行完整写入 `~/backups/pokemon-back/clear-uid<uid>-<date>-<ts>.json`，包含每条记录的字段。
2. dry-run 预览：`--dry` 只列出命中哪些、不动库，确认范围无误再真删。
3. 删除后复核：删除完立刻 `count` 复核该切片剩余数，并打出该用户总记录数做交叉验证。
4. 一键回滚：`--restore <快照>` 把记录塞回。这里有个关键细节——

## 回滚为什么用 upsert 而不是 insert

清库后用户可能又在同一天玩了同名玩法，`(userId, quizType, date)` 唯一键已被占用，盲插会撞 P2002。所以回滚走 upsert：缺的补上、已有的覆盖回快照值，幂等且可重复执行。

```ts
await prisma.record.upsert({
  where: { userId_quizType_date: key },
  update: { solved: r.solved, tries: r.tries, attempts: r.attempts, extra: r.extra },
  create: r,
});
```

快照只取白名单字段，回滚时不带原 `id`，交给数据库重新分配主键，避免和现存主键冲突。

## 生产执行记录

2026-09-25 在服务器实跑（北京时区口径与前端"今日"一致）：

```
ssh drew-server 'cd /var/www/pokemon-back && npx tsx scripts/clear-day.ts'
// dry-run 命中 9 条（type/dex/silhouette/stats/move/ability/item/wordle/pokedoku）
// 真删 9 条 → 校验剩余=0（该用户总记录=118）
```

日期口径统一用 `new Date(Date.now() + 8e3 * 3600).toISOString().slice(0, 10)`，与云函数、小程序端保持一致，避免"服务器时区差一天"这类经典坑。

## 两个边界漏洞

- SprintRecord（冲刺模式成绩）不在清理范围：它无唯一约束、可重复玩，脚本有意不碰。需要清要单独处理。
- 服务端清完还不够：小程序本地缓存 `dqc:<玩法>:common:<日期>` 与 `<玩法>.progress` 仍会让页面显示"今天已完成"，必须连客户端存储一起清。

## 工程复盘

生产环境的"删除"默认应该是可逆操作。快照 + dry-run + 复核 + 回滚这四件套，把一次高危动作拆成"先看清、再确认、留后路"的流程。配套运维也已落地：每日 04:30 SQLite 备份（cp + 文件头校验 + 按天保留 + 超期清理）、日志轮转、健康检查脚本（异常推 Server 酱、同问题 1 小时去重）。更多实现见 blog.alleria.cn。
