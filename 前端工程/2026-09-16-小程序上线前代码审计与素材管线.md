# 微信小程序上线前的代码审计与素材管线实践

## 问题背景

在为「宝可猜谜挑战」微信小程序（原生 + 云开发）准备对外宣传前，需要确保对外陈述的玩法机制、素材规格与代码实现完全一致。直接依赖需求文档或记忆存在漂移风险：宣传稿一旦写出代码里不存在的机制，就是公开事实错误。同时，发布素材（logo）需满足小程序 / 公众号头像 ≤2MB 的体积限制。

## 技术方案

### 1. 素材体积管线（sips）

不引入在线压缩服务，使用 macOS 自带 `sips` 本地处理，保留原分辨率仅重压质量：

```bash
sips -Z 2048 -s format jpeg -s formatOptions 85 in.jpg --out logo_2048.jpg
sips -Z 512 -s format jpeg -s formatOptions 80 in.jpg --out logo_512.jpg
```

注意：若原图为透明底 PNG，转 JPEG 会填白底，需透明 / 圆角的场景应改出 PNG。该命令模板已沉淀为可复用片段。

### 2. 代码审计对齐玩法机制

逐一阅读 `miniprogram/pages/*`、`cloudfunctions/submitResult/index.js`、`cloudfunctions/dailySilhouette/core.js`、`sprint.js`、`silhouette.js`，将实现与设想逐项核对，关键结论：

- 每日机制：每种题型各自每天一道（首页 9 张题型卡 + 冲刺），而非整体一天一次。
- 剪影：`2.0x→1.0x` 渐进揭示，每猜错缩 0.2x，错到后段揭颜色（先主色后副色）。
- 冲刺：30 题 / 180s / 8 种题型混排，跳过 -5s，每题 6 次机会。
- 连胜：`submitResult` 中 `streak = score===5 ? 昨日+1 : 0`，5/5 全对才 +1，错一题清零。

### 3. 平台合规约束

- 流量主：累计独立访客达标（常见 1000 UV），依赖分享 / 好友对战做量，禁止刷量。
- 虚拟支付：微信 2026-08-31 对个人主体开放，但类目须含"工具"、iOS 走 Apple IAP（费率 12%、不可开发者主动退款）。
- 生死线：玩法不可被判定为"游戏"，否则需版号，个人主体无法办理。

## 踩坑记录

- PNG 透明底转 JPEG 白底：发布素材前未确认底色，导致头像底变白，改用 PNG 重出。
- 记忆与实现不一致：曾以为首页"一天一次"，实为每种题型每天一道，宣传口径需按代码修正。

## 工程复盘

发布前的代码审计是把"我以为"变成"我确认"的必要环节。素材管线（sips）、机制对齐（读代码而非读文档）、合规边界（类目 / 支付 / 流量主）三件事共同决定一个独立产品能否合规交付。代码是唯一事实来源，文档和记忆都会漂。
