# 小程序云函数调用量治理与部署前的作用域静态检查实践

## 问题背景

某微信小程序（原生 + 云开发，9 种玩法）的日常函数调用量中，数独玩法云函数 `pokedokuQuiz` 达到 928 次/天，为全项目最高。该玩法为每日一题，单用户单日正常只产生个位数请求，量级明显异常，需要先定位来源再决定优化手段。

同时，本轮改动包含云函数逻辑调整，需要在上线前建立可复用的验证手段——此前仅有 `node --check` 与 lint 两道语法层检查。

## 技术方案

### 一、定位调用量来源

数独页需要展示每格尚可选取的宝可梦数量 `cellCounts`。原实现中，前端每提交一次猜测后额外调用一次云函数，通过 `syncCellCounts()` 重新执行整次 `get` 以获取该字段。单局调用结构为：

```
1 × get（出题） + 9 × guess（猜格） + 最多 8 × sync（校正） = 18 次
```

优化方向明确：让 `cellCounts` 随 `guess` 的返回一起回传，消除额外的校正请求。

### 二、抽取共用纯函数

在云函数中抽出纯函数 `countCells(board, usedNames)`，由 `boardToView()`（服务于 `get`）与 `guess` 共用；`guess` 猜中的返回体中新增 `cellCounts` 字段。

```js
// guess 正确分支
return {
  ok: true, correct: true,
  mon: { id: mon.id, name: mon.name, types: mon.types },
  cellCounts: countCells(board, usedNames),
};
```

兼容性判定（向前兼容，云函数可先行单独部署）：

- 线上旧版前端不读取 `cellCounts`，多返回字段无副作用，仍走原 `syncCellCounts()` 路径；
- 新版前端保留旧云函数兜底：`if (r.cellCounts) patch.cellCounts = r.cellCounts; else if (!r.cellCounts) this.syncCellCounts();`，实现新旧双向兼容。

### 三、部署后暴露的 TDZ 崩溃

上传云函数后线上立即报错，每次调用必失败：

```
ReferenceError: Cannot access 'board' before initialization
    at exports.main (/var/user/index.js:132:20)
```

根因：`if (action === "guess")` 分支块内，第 132 行的重玩（replay）逻辑引用了 `board`，而 `const board = buildBoard(dateStr)` 位于第 159 行。块级 `const` 声明会遮蔽外层第 81 行的 `let board`，使整个 `guess` 块自块顶起进入暂时性死区（TDZ）。

修复方式：删除块内重复声明，统一复用外层 `board`。common 模式下外层即为 `buildBoard(dateStr)`（同值）；replay 模式下外层已在更早处构建为 `buildBoard(replayDate)`，语义正确。附带收益是省去一次棋盘构建。

进一步核对 `git HEAD` 发现，该行在 1.0.6 提交版本中即已存在——说明该版本发布时 `pokedokuQuiz` 并未同步部署，replay 分支从未在真机执行过。此类「前端已上线、云函数未部署」的错配需要在后续排查中继续关注。

## 踩坑记录

### `node --check` 无法覆盖作用域类错误

语法检查通过不代表可运行。TDZ 属于运行时语义错误，只有在实际执行到该语句时才会抛出，静态语法层面完全合法。

### 静态检查工具需先自证有效

引入 eslint 的 `no-use-before-define` 规则扫描云函数：

```bash
npx --yes eslint@8 --no-eslintrc --env node,es2022 \
  --parser-options=ecmaVersion:2022 \
  --rule '{"no-use-before-define":["error",{"variables":true,"functions":false,"classes":false}]}' \
  cloudfunctions/*/index.js cloudfunctions/*/core.js
```

为确认规则确实能捕获该问题，先用含有 bug 的 HEAD 版本试跑，工具精确报出 `127:20` 与 `128:20`——正是线上崩溃的两行；再扫描全部云函数当前版本，输出为空。

### 重玩分支的测试数据需与棋盘日期对齐

运行时测试中，重玩模式的正解必须依据 `replayDate` 当天的棋盘计算。若用当日棋盘的正解去验证重玩分支，会把正确结果误判为错误。

## 工程复盘

本轮沉淀两道上线前门禁，缺一不可：

1. **运行时 harness**：通过 `Module._load` 劫持 `wx-server-sdk`，stub `getWXContext` / `database().collection().where().get()` / `doc().update()` / `add()`，加载真实题库 `core.js` 后直接调用 `main()` 遍历全部分支（`get`、`guess`·common 对/错、`guess`·replay 对/错、`get`·replay、`reveal`、`giveup`、结束后再 `get`），修复后 10/10 通过。
2. **静态作用域检查**：`no-use-before-define` 全量扫描 `cloudfunctions/*/index.js` 与 `core.js`。

线上验证采用云开发控制台的云函数「云端测试」直接传参调用，无需改动数据库：

```json
{ "action": "guess", "mode": "replay", "replayDate": "2026-09-06", "cell": 0, "name": "妙蛙种子" }
```

返回 `ok: true`（判错）即证明执行路径已成功读取 `board.rowConstraints`——既确认 TDZ 已修复，也确认云函数确为最新版本。随后以 `{"action":"get","mode":"replay","replayDate":"2026-09-06"}` 验证 `countCells` 抽取重构后仍返回完整的 9 个计数。replay 分支不读写数据库，是最安全的线上验证路径。

前端侧的并行改动是本地缓存层 `dailyCache`：针对每日题当日固定的特性，接入 7 个玩法页（10 页中排除无 `onShow` 的 2 页与限时冲刺玩法），配合并发锁与命中缓存跳过请求，用于降低切页重拉产生的调用量。该部分只改前端，需重新上传小程序代码生效。

工程结论：云函数部署独立于小程序审核、立即生效，缺少流程约束，因此必须由工具门禁而非人工自查兜住正确性；「前端已上线、云函数未部署」的版本错配，比单点 bug 更难发现，值得单独治理。
