# 微信答题小程序用户流失卡点的数据库量化方法

## 问题背景

小程序上线后收到一条模糊反馈："题目整体难度偏大，普通玩家没思路，建议加提示或跳图鉴查答案"。作为数据驱动决策的常规动作，需要先回答两个问题：用户是真的"太难"放弃，还是"没耐心"乱点放弃？卡点集中在哪些玩法？

## 技术方案

答题记录落在云数据库 `Record` 集合，每次提交一次猜测写一条，字段含 `solved`（是否猜中）、`tries`（已尝试次数）、`quizType`（玩法类型）。量化"没答完就退出"的查询条件如下：

```js
// 各玩法上限在 quizTries.js：8 个玩法 6 次 / 数独 9 次
const maxTriesByType = { item: 6, ability: 6, /* ... */ sudoku: 9 }
const STUCK = await db.collection('records')
  .where({
    solved: false,
    tries: _.lt(maxTriesByType[quizType]) // 未达上限即"中途放弃"
  })
  .count()
```

全库 7705 条记录统计结果：

- 猜中 6743（87.5%），未猜中 962；
- 没答完就停 445 条，占未猜中 46.3%；只猜 1 次就走 245 条（25.5%）；
- 同局相邻猜测间隔中位数 19 秒（P25=10s / P75=40s），<3 秒仅 0.7%；
- 按玩法答完率排序：道具 76%、属性 81%、数独 84%，其余 89%~92%；"猜 1 次就走"集中在道具(38)、属性(43)。

中位数间隔 19 秒直接区分了"没耐心"（应 <3 秒占比高）与"认真看题但没思路"（实际分布），从而把需求从"加跳过按钮"修正为"加提示，且优先道具/属性"。

## 踩坑记录

- "一道都没答就退出"无法从 `Record` 查到：`Record` 在第一次猜测提交时才写入，与"从没打开过"无法区分。改用微信"访问人数 vs 库里有记录"差值估算（≈26~29%），并判断不值得为这个指标专门加埋点。
- 自查基准错误：曾把 `git show HEAD` 当成"改动前"基线，实际 HEAD 已含本次改动，导致误读数据。结论依赖的始终是线上库真实统计，而非本地 diff。

## 工程复盘

用一条带明确语义的查询，把模糊反馈转成可排序的卡点清单，是比开会更快的决策路径。数据还顺带验证了另一处：小红书封面点击率连续两周卡在 19.3%（同类中位数 22.7%），与答题难度是两条独立线索，但同样靠数据而非直觉定位。
