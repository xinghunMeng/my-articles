# 微信云开发接入与宝可梦猜谜小程序的工程化复盘

## 问题背景

在宝可梦猜谜小程序（微信原生小程序 + 云开发 NoSQL）中，题库通过云开发控制台导入，多个玩法由云函数取题、服务端判分。开发过程中连续遇到三类工程问题：数据导入格式约束、云函数运行时崩溃、以及剪影玩法 UI 的两次迭代。本文记录根因与修复。

## 技术方案与踩坑记录

### 1. 云数据库导入的 JSON Lines 约束

云开发控制台导入 .json 文件时，要求内容为 JSON Lines（每行一个对象，不带外层 `[]`）：

```json
{"_id":"q1","type":"flavor","stem":"...","options":["A","B","C","D"],"answer":0}
{"_id":"q2","type":"superlative","stem":"...","options":["A","B","C","D"],"answer":2}
```

导入数组格式会报「导入数据格式不正确，请检查是否为 JSON Lines 格式」。注意控制台只识别 .json 扩展名，.jsonl 无法选入，因此把 JSONL 内容以 .json 后缀保存即可。题库 1209 条（_id q1~q1209）。

### 2. getDailyQuiz 崩溃：漏传第 4 参数

运行时报错 `-504002`，堆栈指向 `pickByType`：`Cannot read properties of undefined (reading 'has')`。

根因：main 调用 `pickByType(type, n, rng)` 漏传第 4 参 `usedStems`，而函数内部依赖它做跨类型题干去重：

```js
// 修复前
const picks = pickByType(type, n, rng); // usedStems 为 undefined -> .has() 崩溃
// 修复后
const usedStems = new Set();
const picks = pickByType(type, n, rng, usedStems);
```

该去重用于避免同日出现「攻击种族值最高」与「防御种族值最高」这类同源题干。修复后与 `data/test_daily.js` 的跨类型去重设计对齐，本地测试（确定性 + 隔日不同）均通过。

### 3. 剪影玩法的资源管线

剪影素材由 Python 脚本从官方 artwork 生成：`gen_silhouette_img.py` 读取 alpha 通道，二值化出透明剪影 PNG（高 200），并同 bbox 生成白底彩图 JPG（高 128），页面叠层对齐。151 只素材 PNG+JPG 共 896KB，整包 0.93MB（主包 2MB 内）。防作弊：素材文件名使用随机 6 位 key，客户端无 key 到名字映射。

### 4. 剪影 zoom 的两次迭代

初次实现为整体缩放（初始 0.6x），用户反馈「一开始就满屏，放大聚焦无效」。改为初始 2.0x 局部放大（中心 25% 可见），每次猜错拉远 0.25x，4 次错后满屏，配合 `.stage { overflow: hidden; transform-origin: center }` 实现渐进揭示。

```js
function computeZoom(wrongs, over) {
  if (over) return 1.0;
  return Math.max(1.0, 2.0 - wrongs * 0.25); // 2.0 -> 1.0 渐进
}
```

## 工程复盘

- 数据正确性：导入格式是隐式契约，应以脚本生成并固化扩展名约定，而非依赖手动导出。
- 崩溃修复：参数契约要和本地测试设计对齐；缺参导致 undefined 访问，应在函数入口对可选参数做默认值兜底。
- UI 迭代：用户截图是第一手需求，zoom 的「局部放大渐进」比「整体缩放」更符合「先露一角」的心理预期。
