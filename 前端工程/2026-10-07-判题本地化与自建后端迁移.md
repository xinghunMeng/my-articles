# 微信答题小程序判题本地化与自建后端迁移：零漂移双跑对拍的工程复盘

category: 后端工程

## 问题背景

宝可梦答题小程序原有 9 个每日玩法，判题全部走微信云开发云函数，每次猜测都打服务端。随着 QQ 端需要独立入口（CloudBase 不互通）以及月调用量逼近上限，需要将判题本地化并迁移到自建后端（Fastify 5 + TypeScript + Prisma 6 + SQLite），且要求"用户无感、答案零漂移"。

## 技术方案

### 判题本地化与零漂移原则

本地不重算取题公式，仅使用云端 `get` 下发的 `dexId` / `abilityId` 等 id 去查包内 `data/pokedex.js` / `data/abilities.js`。该设计从根上避免"前端一份池子、后端一份池子"的漂移——数独玩法早已采用此模式。

验证方式为 Node 双跑：本地模块与云端 `core.js` 各执行一遍后逐字比对，结果 `ability 314 条`、`dex 722 池子 + 3480 组对比板逐字相同`、`silhouette 1025 池子` 全部一致，零漂移。

### 后端"真·双跑对拍"

桩掉 `wx-server-sdk` 后直接调用云函数 `main()`，与后端 handler 做整对象逐字对比，覆盖 9 玩法 × common/replay × 4 种记录状态 + `targetId` 不一致用例，共 138 项全绿。该对拍顺带发现并修复一个真 bug：

```text
// 云端揭晓守卫在自建后端恒为 false（Record 表无 targetId）
if (rec.targetId === target.id) { /* 展示揭晓卡 */ }
// 迁移后删除该守卫，目标由日期确定性推导，结构不会错题
```

修复后把该断言钉进 `audit` 的 `[4b]` 用例，回归即报错。

### 迁移关键取舍

不做服务端权威重算，信任客户端上报的 `correct`。依据：判题已本地化、无排行榜、战绩私有。文档显式声明：若日后引入排行榜，必须把题库并入后端并在 `report` 加校验。

## 踩坑记录

- 对拍自身的两个坑：replay 未传 `replayDate` 时两端各自 `pickReplay()` 随机挑期，表现成 `clues` 不一致（像真 bug）；`ts` 为本次猜测时间，两端 `Date.now()` 差毫秒，比较前需归一。
- `prisma migrate deploy` 不重新生成 Client：新增 `SprintRecord` 模型后必须补 `npx prisma generate`，否则 build 报 `Property 'sprintRecord' does not exist`。
- nginx 逐条列举 `location = /api/xxx`：新接口漏加表现为"本机 curl 127.0.0.1:3200 正常、公网 404"；reload 后旧 worker 仍服务数十秒，易误判为配置错误。

## 工程复盘

迁移类大改动的护城河是可复跑的"双跑对拍 + 守门断言"，把"看起来一样"收敛为"逐字一致"。判题本地化必须让"取题公式"成为单一事实源，避免双份池子漂移。测试纪律上，对拍要取多个且有大值的 seed（小 seed 撞不出 item 冲刺的 `UNIQUE_POOL` 差异）。最终 `test-guess` 32 项、`test-sprint` 241 项全绿，前端切 self 模式后库记录自动增长，确认端到端跑通。
