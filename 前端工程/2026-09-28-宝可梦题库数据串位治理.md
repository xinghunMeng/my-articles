# 宝可梦题库两处数据串位的根因与多副本一致性治理

## 问题背景

两个用户可见的数据错误：特性"款待"的线索卡显示成"面影辉映"的官方说明；图鉴里美录梅塔被标为"第 1 阶段"（应为第 2）。两者均不报错、不影响答题，但数据正确性被破坏，属于典型"静默脏数据"。

## 根因

1. 特性文案串位：文案源为官方中文 dump，按数字 id 取（`TOKUSEIINFO_<id>`）；本地编号来自 PokeAPI。两套编号在第九世代尾部不一致（款待本地 301 / 官方 299）。一次全量刷新按 id 覆盖，将 299~311 整段错位，共 11 条错。招式池因编号一致无此问题。
2. 进化阶段错标：进化链取自 PokeAPI 的 `evolution-chain` 快照（旧：808/809 各为独立根链）；现官方合并为 `chain 428 = meltan -> melmetal`。快照过期导致生成两个独立家族，stage 全为 0，输出"第 1 阶段"。

## 技术方案

- 特性对齐键由数字 id 改为"官方中文名"：官方 dump 重建为"中文名 -> 说明"映射，按名对齐；同名多 id 变体合并；新增串位判据（描述恰好是池内另一条官方文本 → 判坏值重取），默认模式自愈，不再依赖 `--official`；补 `--dry`/`--all` 开关。
- 进化链全量重跑：`fetch_evo_chain.js -> fetch_evo_stage.js -> merge_stage.js -> gen_riddle_pool.js -> gen_dex_ext.js -> gen_pokedex.js`。
- 修复 `gen_dex_ext.js` 形状陷阱：typeQuiz 的对比板需读 `target.bst`/`target.stage`，此前被写成瘦形状（无 bst/stage）；改为 typeQuiz 复制 dailyRiddle、statsQuiz 保持瘦形状（bst 现算、stage 读 stage_map），并在注释写清两份形状故意不同。

## 踩坑记录

- 阶段数据有 9 个落点（前端 5 处 + 云函数 6 份中带 stage 的 3 份 + statsQuiz 1 份；后端 4 份），特性池 3 份副本（data / 云函数 / 后端，后端那份无脚本、需手动同步）。任何一处漏改都会产生"半对"状态。
- 自查基准错误：用 `git show HEAD` 当改动前基准，因改动已提交，比对全空。正确基准是改动前 commit（`d8b5806^`）。该错误掩盖了真实遗漏——百科首页卡片"541 个家族"漏改 540，且仅存在于工作区未提交。

## 工程复盘

数据散落多处时，把它当契约来测而非当文本来改。配四套审计脚本（audit_pools / audit_stats_dual / test_kb / test_pokedex + 后端 audit:puzzle），全绿才发版。对齐键选"稳定的唯一标识"（名字）而非"易漂移的代理键"（id）。认知上：快照不等于永远正确，要有再对账机制。部署：后端 `npm run build && pm2 restart` 即时生效；小程序随下次发版。更多见 blog.alleria.cn。
